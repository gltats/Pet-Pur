# 🐾 Pet&Pur

*Find your purrfect match!*

We're building **Pet&Pur**, a pet-friendly dating web application that brings people together through romantic compatibility, shared interests, and their love for animals.

As part of the **42 Matcha project**, we want to explore a more inclusive and personalised approach to online dating. Our goal is to create a platform where people can find meaningful connections while considering not only their romantic preferences but also their lifestyles, pets, allergies, and animal-related dealbreakers.

We believe that finding the right match goes beyond two people getting along — their furry (or not-so-furry) companions matter too!

## 🚀 Getting Started

### 1. Clone the repository

```bash
git clone https://github.com/gltats/Pet-Pur.git
cd Pet-Pur
```

### 2. Environment configuration

We'll document the required environment variables as we develop the application.

We'll keep sensitive information, such as passwords, API keys, and database credentials, out of version control by using local `.env` files. Please refer to .env.example.

### 3. Start Pet&Pur with Docker Compose

We use **Caddy** as our web server and reverse proxy. Currently, Caddy serves our static `index.html` over HTTPS, using a locally generated TLS certificate.

Our Docker Compose setup handles the container configuration, while Caddy manages HTTPS and certificate generation.

#### Start the application

From the project root, validate our Docker Compose configuration and start the services:

```bash
docker compose config -q
docker compose up -d
```

Once running, our test page is available at:

**https://localhost:8443**

When opening the page for the first time, your browser may display a certificate warning. This happens because Caddy's local certificate authority isn't automatically trusted by your operating system.

Follow the instructions below to configure certificate trust.

#### Configure HTTPS certificate trust (macOS)

Caddy automatically generates a local certificate authority (CA) to secure `localhost`. However, because Caddy runs inside Docker, macOS doesn't automatically trust it.

Each developer must configure certificate trust on their own computer.

**1. Export the root certificate**

With Caddy running, execute the following command from the project root:

```bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./caddy/root.crt
```

This copies Caddy's public root certificate from the container to `caddy/root.crt` on your computer.

**2. Import the certificate into macOS**

- Open **Keychain Access**.
- Select the **System** keychain.
- Import the `caddy/root.crt` file.
- Locate the imported Caddy certificate and double-click it.
- Expand the **Trust** section.
- Set **When using this certificate** to **Always Trust**.
- Close the window and authenticate if prompted.

Only trust the certificate generated by your own local Caddy instance.

**3. Verify the HTTPS connection**

Once the certificate is trusted, run:

```bash
curl https://localhost:8443
```

If everything is configured correctly, we'll receive the HTML content of our test page without certificate verification errors.

We should also be able to open **https://localhost:8443** in our browser without a certificate warning.

**Linux (Ubuntu):** We'll document the certificate trust procedure once we've tested our setup on Ubuntu.

#### Troubleshooting

If Caddy doesn't start or our page isn't accessible, we can check the status of our containers and inspect Caddy's logs:

```bash
docker compose ps
docker compose logs caddy
```

**Certificate storage and security**

We use a Docker named volume (`caddy_data`) to preserve Caddy's certificate authority and TLS data between container recreations.

Locally generated certificates and private keys should remain outside version control. Each developer should use their own local certificate authority rather than sharing private CA keys.

**Testing HTTPS without certificate trust**

If we prefer to test the application without configuring certificate trust on our computer, we can use:

```bash
curl -k https://localhost:8443
```

The `-k` option skips certificate verification while keeping the HTTPS connection encrypted.

This is useful for quick local testing, but it does not verify the server's identity and should not be used as a permanent solution.

To access the application through a browser without certificate warnings, we'll still need to configure certificate trust as described above.

#### Stop the application

To stop and remove our running containers:

```bash
docker compose down
```

Our Docker named volume is preserved by default, allowing Caddy to reuse its certificate data the next time we start the application.


## 🌿 GitHub Workflow

To keep our development organised and maintain code quality, we've decided to follow a **branch-based workflow with pull requests**.

Our `main` branch is protected, meaning we won't push changes directly to it.

### Branch Naming

We'll use descriptive branch names following this convention:

```text
type/short-description
```

Examples:

```text
feat/user-authentication
fix/login-validation
chore/project-setup
ci/github-actions
docs/update-readme
```

### Conventional Commits

We'll follow the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) specification to keep our commit history clear and consistent.

**Format:**

```text
type(scope): short description
```

| Type | Purpose |
|---|---|
| `feat` | Introduce a new feature |
| `fix` | Fix a bug |
| `chore` | Maintenance or project setup |
| `ci` | GitHub Actions and CI configuration |
| `build` | Build system, Docker, or dependencies |
| `docs` | Documentation changes |
| `refactor` | Improve code without changing behaviour |
| `style` | Code formatting (not UI styling) |
| `test` | Add or update tests |
| `perf` | Performance improvements |

Examples:

```bash
git commit -m "feat(auth): add user registration"
git commit -m "fix(api): handle invalid requests"
git commit -m "ci: configure automated linting"
```

### Pull Requests

We've established the following process:

1. We'll create a new branch from the latest `main`.
2. We'll commit our changes following Conventional Commits.
3. We'll open a pull request for review.
4. We'll ensure that all required automated checks pass.
5. We'll review each other's code and require one approval before merging.
6. We'll resolve review discussions before merging.
7. We'll use **Squash and Merge** to maintain a clean commit history.

## ✅ Code Quality & Linting

We want to maintain consistent coding standards throughout Pet&Pur. We'll use automated formatting, static analysis, testing, and build validation to help us catch problems early.

| Component | Tool | Purpose |
|---|---|---|
| Rust | rustfmt | Check consistent code formatting |
| Rust | Clippy | Detect suspicious or unnecessarily complex code patterns |
| Rust | Cargo Test | Run automated tests |
| React | ESLint | Detect code quality issues |
| React | Build check | Verify the frontend builds successfully |
| Caddy | Caddy validation | Validate the web server configuration |
| Docker | Docker Compose | Validate our service configuration |

### Local Checks

**Rust** (once the backend is initialised):

```bash "
cd backend
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test
```

**React** (once the frontend is initialised):

```bash "
cd frontend
npm run lint
npm run build
```

**Docker Compose:**

```bash "
docker compose config -q
```

**Caddy:**

```bash "
docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile
```

### GitHub Actions

We use GitHub Actions to run automated checks whenever we open or update a pull request targeting `main`.

Our workflow will expand as the frontend, backend, and database are implemented. Once configured as required status checks, these validations will help prevent changes that fail our quality standards from being merged.
